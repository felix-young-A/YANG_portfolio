## 1. Obsidian 格式规范

**引用与 Callout 的使用原则（看场景用，不滥用）**：

本技能产出的笔记**支持普通引用块 `>` 与 Obsidian Callout 两种形态**，按场景选用；**禁止的是"满屏符号块"的滥用**，而不是符号块本身。

**普通引用块（默认形态）**：

总结、原话引用、嘉宾发言、关键结论等**默认使用普通 `>` 引用块**；如需强调可换对应 Callout（见下表），关键是**按场景用、不滥用**。

```markdown
> 摘要或关键引用写在这里，每行以 > 开头。
> 支持多行。
```

**Callout 全部按场景选用（不禁止任何类型，但数量克制）**：

| Callout 类型   | 适用场景                 | 示例                           |
| ------------ | -------------------- | ---------------------------- |
| `[!note]`    | 章节摘要、段落小结（**可折叠**）   | `> [!note]- 本节摘要`            |
| `[!info]`    | 信息提示、补充说明            | `> [!info] 补充：该概念最早由...`     |
| `[!tip]`     | 技巧、方法论、可复用经验         | `> [!tip] 实操建议：...`          |
| `[!warning]` | 风险提示、坑点、注意事项         | `> [!warning] 注意：此方法仅适用于...` |
| `[!quote]`   | 精彩原话、金句级引用（**克制使用**） | `> [!quote] 原话内容 —— 说话人`     |

**使用红线（防止掉质量）**：
- **按语义使用，不装饰**：只有内容确实属于"摘要/提示/风险/金句"才用对应 Callout（金句用 `[!quote]` 时务必克制）；普通叙述段不用符号块包裹
- **数量与场景（看语境，不设死板红线）**：Callout 不是禁用项，也不设"全文必须 ≤N 个"的硬性上限；判断标准是**语境与情况**——折叠摘要用 `[!note]-`、重要风险提示用 `[!warning]`、可复用方法用 `[!tip]`、金句级原话用 `[!quote]`。但**默认以普通 `>` 引用为主**：日常笔记通常只有顶部折叠摘要 1 个 Callout，其余引用一律先考虑普通 `>`，仅当内容确实需要强视觉强调、且语境强匹配时才升级为 Callout。切忌为了"排版丰富"满屏符号块
- **默认优先普通 `>` 引用**：总结、原话引用、嘉宾发言、关键结论、补充说明、操作建议等，先用普通 `>` 引用块；当需要更强的视觉强调、且内容确实匹配 Callout 语义时，按语境升级为对应 Callout
- **不依赖 Callout 排版**：正文本身必须结构清晰，删掉所有 Callout 后笔记依然完整可读——符号块是锦上添花，不是骨架
- 禁止 `<details>` / `<summary>` 折叠标签（Obsidian 用 `> [!note]-` 原生折叠）
- 金句/结论独立成段或加粗即可，不必都包成 Callout

**其他 Obsidian 规范**：

- **内部链接**：使用 `[[笔记名]]` 语法，例如 `📂 [[Field_Notes.base|Field Notes 索引]]`
- **标签**：使用 YAML frontmatter 中的 `tags` 字段，不在正文中使用 `#标签` 语法
- **frontmatter**：必须包含 `title`、`source`、`date`、`created`、`tags` 等标准字段
- **图片引用**：使用标准 Markdown 语法 `![说明](相对路径)`，不要使用 HTML `<img>` 标签
- **不要使用 GitHub Flavored Markdown 特有但 Obsidian 不支持的语法**（如任务列表复选框 `- [ ]`、emoji 短代码等在某些场景下）

## 2. 排版规范

**段落控制**：

- 每个子主题（`####`）下的每个段落控制在 **2~4 句话**
- 段落之间**必须用空行分隔**
- **超过 5 行的段落必须拆分**为多个段落
- 避免一行一句（过于碎片化，信息密度太低）
- 避免巨大段落（一个子主题下一整块文字，阅读体验极差）

**正确示例**：

```markdown
#### 羊群效应与市场气氛

羊群效应是行为金融学中的核心概念之一，指的是投资者在信息不充分时倾向于模仿他人的决策行为。在市场上涨阶段，大量投资者跟风买入；在下跌阶段，则集体恐慌抛售。

这种行为模式在 A 股市场尤为明显。2015 年的牛市中，大量散户在市场高点涌入，导致估值严重偏离基本面；而随后的暴跌中，恐慌性抛售又加剧了市场下跌幅度。
```

**错误示例（避免）**：

```markdown
#### 羊群效应与市场气氛

羊群效应是行为金融学中的核心概念之一，指的是投资者在信息不充分时倾向于模仿他人的决策行为。在市场上涨阶段，大量投资者跟风买入；在下跌阶段，则集体恐慌抛售。这种行为模式在 A 股市场尤为明显。2015 年的牛市中，大量散户在市场高点涌入，导致估值严重偏离基本面；而随后的暴跌中，恐慌性抛售又加剧了市场下跌幅度。巴契里耶在 1900 年的博士论文中已经指出了市场价格的随机性特征，这与羊群效应形成了有趣的对比。
```

**子主题拆分**：

- 每个视频章节（`###`）下应有**多个子主题（`####`）**，不能只有一个大段落
- 子主题数量建议：**每个大章节 3~9 个子主题**
- 子主题标题应**概括该段落的核心内容**，使用有意义的标题：
  - 正确：`#### 羊群效应与市场气氛`、`#### B股市场的历史表现`
  - 错误：`#### 第三部分`、`#### 关于市场的内容`
- 如果某个章节内容很少，可以合并到相邻章节，不要创建只有一个子主题的章节

**视觉节奏**：

- 每个章节（`###`）之间用 `---` 分隔线隔开
- 重要观点可以单独成段，前后留空行，形成视觉焦点
- 列表项控制在 1~2 行，不要写成段落式的长列表项
- Callout 和普通引用块按场景适度使用，不要滥用（每个子主题最多一个 Callout，全文 5~8 个以内）
- 代码块、引用块、表格等富文本元素交替使用，避免全是纯文字

## 3. 视频链接与 iframe 校验

嵌入视频时，优先使用 iframe 嵌入原始视频播放器。

**平台 iframe 策略**：

| 平台       | iframe 策略                                                                                                                                                                                                                                                                                                                                                                                           |
| -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Bilibili | `<iframe src="https://player.bilibili.com/player.html?isOutside=true&bvid=BV_ID&cid=CID&p=1&autoplay=0&danmaku=0" width="100%" height="400" scrolling="no" border="0" frameborder="no" framespacing="0" allowfullscreen="true"></iframe>` — `cid` 必需，通过 API `https://api.bilibili.com/x/web-interface/view?bvid=BVxxx` 获取 `data.cid`，或在视频页面 F12 Console 执行 `window.__INITIAL_STATE__.videoData.cid` |
| YouTube  | `<iframe src="https://www.youtube.com/embed/VIDEO_ID?autoplay=0" width="100%" height="400" frameborder="0" allowfullscreen></iframe>` — 标准嵌入                                                                                                                                                                                                                                                        |
| 抖音       | **若尝试后不支持稳定 iframe 嵌入**，只保留安全链接：`> 📺 [抖音](原始链接)`                                                                                                                                                                                                                                                                                                                                                   |
| 小红书      | **若尝试后不支持 iframe**，仅保留链接：`> 📺 [小红书](原始链接)`                                                                                                                                                                                                                                                                                                                                                         |

**通用规则**：

- iframe 必须指向当前正文所讨论的**主视频**，不能指向推荐视频或相关视频
- 如无法确认主视频 ID，只保留安全链接，不嵌入 iframe
- 所有 iframe 默认关闭自动播放（`autoplay=0`）

**查找可嵌入视频的顺序**：

1. 先检查原页面是否有 embedded video、iframe、播放器源码、YouTube、Bilibili 或原站播放器链接
2. 搜索 YouTube：用创作者名、嘉宾名、主题词、书名、原英文标题和可能的替代标题组合搜索。注意 YouTube 标题可能与 Substack/播客标题不同
3. 搜索 Bilibili：优先使用嘉宾中文名 + 内容关键词；其次用创作者中文名 + 嘉宾名；再次用主题词、书名、中文译名或金句搜索。B 站标题常常突出嘉宾、观点或金句，不一定包含创作者名
4. 至少尝试 2 到 3 组关键词组合，横跨 YouTube 和 Bilibili；不要只搜一次就放弃
5. 如有用户明确偏好，按用户偏好选择首个 iframe；否则默认优先选择更稳定可访问的公开视频 iframe
6. 如果 YouTube 和 Bilibili 都有同一主视频，`## 🎬 Video` 下方必须同时列出 `[YouTube]`、`[Bilibili]`、`[官网]` 快速入口
7. 最后兜底才使用原站/Substack/Mux/播客页面链接；不要下载视频到最终工作区

**校验规则**：

- iframe 必须指向当前主视频，不能使用 companion interviews、related videos、推荐视频、页面中的其他嵌入视频或同系列但不同主题的视频
- 至少比对标题、作者/频道、嘉宾、时长、发布日期、字幕开头内容或页面描述中的**两项**
- 如果 iframe 与当前文稿来源不一致，宁可写"待确认"，不要放错 iframe
- 如果只找到原站播放器字幕或文稿，但没有找到可验证的 YouTube/Bilibili 主视频链接，则保留 `## 🎬 Video`，但只列安全链接：
  - `> 📺 YouTube: 待确认`
  - `> 📺 Bilibili: 待确认`
  - `> 📺 [官网](原链接)`
- 如果所有搜索都失败且没有可工作的原站链接，应询问用户是否能提供 YouTube/Bilibili 链接；不要默默跳过，也不要留下坏 iframe

## 4. 语言与标题规范

- 文件顶级模块标题使用**英文**（如 `TRIGGERS`、`TASK TYPES`、`CORE RULES`、`Abstract`、`Key Points`、`Full Transcript`、`Content`、`Related Notes`）
- 正文内容使用**中文**
- frontmatter 中的 `description` 不重复正文中已有的信息
- 输出文件命名：`{来源平台}-{视频/文章ID或slug}`，如 `bilibili-BV1xx...`、`wechat-abc123`

## 5. frontmatter 与标签规范

**frontmatter 字段规则**：

- `host` / `author` / `guest` / `source` / `date` 等字段使用**纯文本**，禁止 `[[wikilink]]`
- Wikilinks 在 frontmatter 中会被当作字面文本，不是链接引用
- frontmatter 中的信息**不要在正文重复堆叠**（铁律）

**标签规则（Iron Rule）**：

-  **2 个以上五个以下左右贴切标签**
- 标签 1（固定）：`fieldnote`
- 标签 2（内容类型）：`article` / `interview` / `paper`，根据笔记实际语义内容与主题选择
- 其他：根据内容语义，主题，内容方向来选定，要贴题，有符合特征值
- 示例：`fieldnote + article` ✅ · `fieldnote + interview` ✅ · `fieldnote + 文学` ❌

## 6. 关键帧截图与图片交付

如果视频里有真正有知识价值的画面，可以截取少量关键帧；不要为了装饰而截图。

**适合截图的内容**：

- 产品界面、工具界面、操作流程
- 流程图、架构图、表格、步骤说明
- Spec、Prompt、代码、API 文档、配置页面
- 关键结果展示，例如假 MVP 页面、最终生成效果、对比图
- 能帮助理解一个知识点的证据画面

**不适合截图的内容**：

- 普通口播画面
- 重复画面
- 转场、封面、表情包、纯装饰画面
- 没有信息量的画面

**截图规则**：

- 默认不保存整段视频
- 通常截取 **3 到 6 张**关键帧，少而精
- 图片优先保存为压缩后的 `webp`；不可用时用 `jpg` 或 `png`
- 图片保存到 `assets/[note-slug]/` 目录
- Markdown 中使用相对路径引用图片，不使用 base64 内嵌图片
- 默认使用标准 Markdown 图片语法：`![图片说明](assets/[note-slug]/image-name.webp)`
- 图片必须放在对应知识点段落附近，不要集中堆在文末，除非用户明确要求 Key Frames 区
- 如果可以直接将图片以外部图床的可渲染链接的方式嵌入，优先链接形式

**交付规则**：

- 默认总是生成 **Markdown 单文件**，供用户先查看内容
- 默认总是生成 **ZIP 完整包**，供用户满意后下载导入 Obsidian
- ZIP 中必须包含 Markdown 文件；如果有用户需要的图片，还必须包含 `assets/` 图片目录，并保持相对路径可用
- 如果包含截图，ZIP 是必须交付项
- 最终回复先给 Markdown 链接，再给 ZIP 链接
- 中间文件（音频、视频、模型、转写底稿、临时脚本）只放临时目录，**不放入最终工作区**

**ZIP 结构示例**：

```text
note-title.md
assets/
  note-title/
    01-fake-mvp-page.webp
    02-core-flow.webp
    03-spec-document.webp
```

**Markdown 图片引用示例**：

```markdown
![假 MVP 页面：页面看起来完整，但后端能力未真实跑通](assets/note-title/01-fake-mvp-page.webp)
```

## 7. 文件命名

- 文件名来自原内容标题：视频用视频标题，文章用文章标题
- 如果标题本身是英文，文件名保留英文含义并转为安全文件名
- 如果标题不是英文，先翻译成英文，再转为安全文件名。
- 文件名使用小写英文、数字和连字符
- 不使用中文、空格、标点和特殊符号

示例：

```text
vibe-coding-02-beginners-build-products-first-run-the-main-flow.md
bilibili-BV1xx-xxx-interview.md
wechat-abc123-article.md
```

## 8. 通用格式要求

- 顶级模块标题使用英文
- 正文、摘要、要点和说明文字默认使用简体中文
- frontmatter 中的信息不要在正文重复堆叠
- base link 放在 frontmatter 后面第一行：`📂 [[Field_Notes.base|Field Notes 索引]]`
- 默认使用 `fieldnote` 加内容类型两个 tag
